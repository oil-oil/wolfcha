# 多人模式发布检查清单

多人模式发布前必须逐项通过；规则、生命周期、AI、权限和 UI 任一项失败都不能上线。

## 核心玩法

- 1 名或 2 名真人均可开局，剩余席位由 AI 补齐。
- 身份分配、夜间行动、警长竞选、发言、投票、遗言、猎人、白狼王、警徽移交和胜负结算与单人规则一致。
- 公共状态不泄漏角色、账户 ID、女巫信息、预言家记录或狼队信息。
- 同一 `commandId` 幂等；过期版本无副作用。

## AI 决策

- AI 的发言和全部行动均来自模型；规则引擎只校验合法性和推进阶段。
- 每个 AI 有稳定人格、推理方式和风险偏好，并只读取其角色允许的信息。
- 模型失败最多重试 3 次；失败后事务不落库，不允许随机目标或模板发言冒充模型决策。
- 真人超时或主动离开后，同座位、同角色转入 AI 托管。

## 生命周期

- 房主离开时原子转移房主；最后一名真人离开时关闭房间。
- 真人断线在截止时间内可恢复；超时后自动托管，牌局不永久等待。
- 房主可在大厅关闭房间；普通玩家可退出。
- 开局失败、房间关闭时释放局数占用；占用记录支持过期回收。

## UI 与设备

- 检查宽度：390、393、430、768、769、980、1280、1440。
- 动作栏不得横向溢出，并避让 `safe-area-inset-bottom`。
- 当前发言者、可选目标、已提交状态、连接状态和本轮倒计时必须清晰可见。
- 新消息自动跟随；AI 发言沿用现有语音设置与 TTS 队列。
- 退出、关闭房间必须二次确认。

## 数据库与发布

- 先在本地 Supabase 执行全部迁移，再运行多人测试、TypeScript、限定 ESLint 和生产构建。
- 线上迁移必须单独审批，禁止在功能验证时直接修改线上数据库。
- 发布时 Web 与游戏服务器必须使用同一提交，且游戏服务器必须配置持久化 Supabase Store 和 AI 服务密钥。
- Web 镜像使用 `Dockerfile`，游戏服务使用 `Dockerfile.game-server`；游戏服务 `/health` 通过后才发布 Web。
- 当前生产游戏服务固定单实例；未接入跨实例 Socket 适配器和分布式任务锁前禁止直接扩容副本数。
